# Task description and requirements

## Problem statement

Build an AI-enabled backend service that answers questions about clinical trials by converting a natural-language request into a structured visualization specification. The service must use the ClinicalTrials.gov Data API as its authoritative source. A frontend is not required, but the response must be sufficiently explicit and stable for a frontend engineer to render the visualization without inference.

The central flow is:

1. Accept a natural-language question, optionally accompanied by structured filters.
2. Interpret the requested analysis and retrieve relevant ClinicalTrials.gov data.
3. Decide whether a visualization is appropriate and select a suitable visualization type.
4. Aggregate or transform the retrieved records into visualization-ready data.
5. Return a structured specification, metadata, and—if implemented—record-level traceability for each visualized datum.

The assignment has an approximately 24-hour expectation. It permits any language, libraries, AI tools, and internet access.

## Authoritative source

- **Source:** ClinicalTrials.gov Data API
- **Documentation:** <https://clinicaltrials.gov/data-api/api>
- The implementation may use any API endpoints and fields needed.
- API-derived records, rather than model-generated facts, must underpin values shown in a visualization.

## Functional requirements

### Request/input

The service must accept a request containing:

| Field | Required | Type | Purpose |
| --- | --- | --- | --- |
| `query` | Yes | string | Natural-language question about clinical trials. |
| Additional structured fields | No | Candidate-defined | Optional filters or context that narrow and disambiguate the request. |

The candidate must define, validate, and document every optional field. Suggested examples in the brief include `drug_name`, `condition`/`disease`, `trial_phase`, `sponsor`, `country`/`location`, `start_year`, and `end_year`; these are examples rather than mandatory fields.

### Request interpretation and retrieval

The backend must interpret the query, retrieve relevant ClinicalTrials.gov data, and identify the analytical intent. It should use the query and any supplied filters to select appropriate API fields, filters, aggregation, and grouping.

### Visualization response

Every successful answer must be a structured visualization response. The visualization object must provide:

- `type` — chart/graph type, such as `bar_chart`, `time_series`, or `network_graph`.
- `title` — a human-readable title.
- `encoding` — an explicit mapping from data fields to visual channels, for example x-axis, y-axis, series, nodes, and edges.
- `data` — the records or data points required to render the result.

The response must also include metadata required for correct rendering, such as units, sort order, time granularity, grouping choices, query interpretation, applied filters, and assumptions where relevant. The final response schema must be documented so the renderer never has to guess at semantics.

### Visualization coverage

The service may support any chart types, but should support several coherent query classes. The brief specifically calls out:

- bar and grouped bar charts;
- timelines/time series;
- scatter plots;
- histograms; and
- network graphs across drugs, sponsors, conditions, investigators, or sites.

Broader coverage and meaningful relationship/network visualizations receive stronger evaluation than a narrowly hard-coded chart solution.

### Example question classes

The appendix gives non-exhaustive examples:

- **Time trends:** trial counts per year for a drug or condition.
- **Distributions:** trials by phase; common intervention types.
- **Comparisons:** phases for two drugs; sponsor categories across conditions.
- **Geography:** countries with the most recruiting trials for a condition.
- **Relationships:** sponsor-to-drug networks; drug co-occurrence networks for combination studies.

Supporting every example is not required; they establish the desired breadth.

### Bonus: deep citations

As a bonus, each plotted datum (for example a bar, time bucket, or network node/edge weight) can include references to every—or an appropriate set of—contributing trial records. Each reference should contain:

- `nct_id`; and
- an exact supporting excerpt from the API response, or a specific source field/value.

This requirement makes the output auditable and lets consumers trace aggregate values back to the ClinicalTrials.gov records that produced them.

### Submission deliverables

The final submission must be a ZIP archive containing:

1. All source code required to run the service.
2. A README covering installation/configuration/startup, request and response schemas, key design decisions/trade-offs, limitations, and improvements for additional time.
3. Three to five example queries with the actual JSON outputs generated by the system.
4. Optionally, a small UI, deployed endpoint, or short demo video.

The README must also briefly disclose tools used, how correctness was validated, and which portions were deliberately designed versus generated and adapted.

## Non-functional requirements and evaluation signals

Although not written as formal service-level objectives, the evaluation criteria imply these quality requirements:

| Area | Weight | Practical expectation |
| --- | ---: | --- |
| System design | 35% | Clear decisions, maintainable/extensible boundaries, and sensible handling of real API data. |
| AI/agent design | 20% | Constrain model behavior, avoid hallucination-prone steps, and use validation plus sensible planning/tool use. |
| Code quality | 20% | Readable, organized, correct, robust code and documentation. |
| Query/visualization coverage | 15% | Multiple question classes without one-off hacks; richer visualizations improve the result. |
| Input/output design | 10% | Unambiguous, frontend-friendly, well-structured schemas. |

Deep citations are additional positive consideration. The integrity note explicitly permits AI tools; it values engineering judgment, validation, deliberate design, testing, and iteration.

## Key design considerations

### Trust boundaries and hallucination control

- Treat ClinicalTrials.gov API responses as the source of truth for all visualized values.
- Restrict AI output to a validated intent/plan and a constrained visualization vocabulary; do not let it invent data, arbitrary fields, or unsupported aggregations.
- Validate the interpreted plan against supported operations before retrieval and validate the final response against the published output schema.
- Preserve the original query, resolved filters, and query interpretation in metadata to make results explainable.

### Data normalization and aggregation

- Clinical trial records are heterogeneous and may have missing, multi-valued, nested, or inconsistently formatted fields.
- Define normalization rules for phases, intervention names/types, sponsors, recruitment status, countries/locations, dates, and identifiers before creating aggregations.
- Explicitly define treatment for missing/unknown values, multiple phases/interventions, date precision, duplicate records, and partial API results.
- Make time bucketing, sorting, grouping, and count semantics deterministic and visible in the response metadata.

### Visualization contract

- Use a small, documented visualization type vocabulary with type-specific encoding requirements.
- Separate semantic data from rendering hints. A frontend should receive a clear field-to-channel mapping and data it can render directly.
- Use explicit schemas for categories, time points, numeric measures, network nodes, and edges.
- Include empty-result and unsupported-query response shapes so clients can handle them predictably.

### API reliability and reproducibility

- Plan for pagination, API limits, timeouts, malformed or incomplete records, and API schema changes.
- Bound retrievals and record limits, communicate sampling/truncation if it occurs, and avoid silently presenting partial results as complete.
- Consider caching and request timeouts only after correctness is established; record source/version/query context needed to reproduce a result.

### Traceability and privacy

- Deep citations should link each aggregate datum to source NCT IDs and exact supporting field values/excerpts.
- Avoid logging secrets and define safe handling for configuration such as API keys, even if the selected endpoint does not require authentication.

### Delivery strategy

- Prioritize an end-to-end vertical slice with precise schemas and reliable API-backed aggregates before expanding visualization breadth.
- Add query classes through reusable interpretation, retrieval, normalization, aggregation, and rendering-contract layers—not per-query special cases.
- Provide real, reproducible example outputs and tests against representative fixtures and API responses.
